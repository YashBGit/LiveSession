Writing code is only the beginning

How do we know we built the right thing, and built it correctly?

Software engineering is more than making code run. We also need to know whether the software behaves correctly, whether it meets its specification, whether it solves the user's real problem, and whether security was built in from the start.

One worked example the whole way through: a familiar login page. TDD stands for Test-Driven Development.

Requirements · 1 min 30 secSlide 04 / 13 · 3:30–5:00

From features to requirements

  • REQ-01 The system shall allow a registered user to authenticate with an email and a password.
  • REQ-02 The password field shall hide entered characters by default.
  • REQ-03 The user shall be able to toggle password visibility.
  • REQ-04 Invalid credentials shall be rejected, without revealing which field was wrong.
  • REQ-05 A new password shorter than the minimum length shall be rejected.
  • REQ-06 The system shall not rely on client-side logic alone to enforce authentication.
Every requirement gets an ID so we can trace it to the test that checks it. REQ-05 is the rule we build with TDD later. REQ-06 is about security, and we come back to it.

Requirements are agreed with users and stakeholders, and checked back with them. That check is where validation begins.

Testing · 2 min 30 secSlide 05 / 13 · 5:00–7:30

Testing at three levels

Level 1 · Unit test

One function, on its own. No browser, no database, no network.

is_valid_password("abc")
→ False

Level 2 · Integration test

Two parts talking to each other, for real.

The login form sends credentials to the authentication service and handles what comes back.

Level 3 · Functional / UI test

The system driven the way a user would drive it.

Click show / hide and confirm the password really does become visible.

Careful: typing a username and password into a real web page is not a unit test. Depending on scope it is a functional, integration, system or end-to-end test.
Classify: we check, through the browser, that the Sign in button stays disabled until both fields are filled. Which level is this?
Definitions · 2 min 30 secSlide 06 / 13 · 7:30–10:00

Testing, verification, validation

Testing

An activity: exercise the software and observe.

Run the login flow. Try a short password. The evidence it produces serves both verification and validation.

Verification

Did we build the product according to the specification?

Trace REQ-04 to the test that checks it: does the code conform? Tests are one route; reviews, static analysis and formal proof are others.

Validation

Did we build the right product for the user's real need?

Is this login process usable and appropriate? Were the requirements themselves correct?

Verification: are we building the product right?
Validation: are we building the right product?
◆
Limits of testing: tests can show the presence of bugs, never their absence (Dijkstra). That is why high-integrity systems also need formal verification.
Scenario A: we ask the client whether this sign-in journey suits their staff.
Scenario B: we trace each requirement to the test that checks it.
Secure development · 1 minuteSlide 07 / 13 · 10:00–11:00

Where the trust boundary sits

Suppose this login is verified against every requirement and validated with users. Is it secure?

In the browser: not trusted

  • HTML, CSS and JavaScript are handed to the user
  • The user can read and change all of it
  • Checks here give fast, friendly feedback
  • They cannot enforce anything

On the server: trusted

  • Credentials are actually verified
  • Sessions and tokens are issued
  • Authorisation decisions are made
  • Rules are enforced, whatever the client sends
“A login page that works is not automatically a secure login system.” That is why REQ-06 exists: security is a requirement from the start, with its own tests.

Behind every login is real people's data. Protecting it is a professional, ethical and data-protection responsibility.

Secure development · 1 minuteSlide 08 / 13 · 11:00–12:00

Which one can the user defeat?

In the browser (JavaScript)

// login.js - runs on the user's machine
if (localStorage.getItem("loggedIn") === "true") {
    showDashboard();
}

On the server (Python, Flask)

# app.py - runs on our server (REQ-06)
@app.route("/dashboard")
def dashboard():
    if "user_id" not in session:
        abort(401)
    return render_dashboard(session["user_id"])
Which check can the user defeat?
How would someone defeat it?

Anyone can open the browser's developer tools, set loggedIn to "true" and refresh. On the server, the session is signed and checked on every request, so editing the browser changes nothing: the server decides.

Keep the client check: it gives fast, friendly feedback. It just cannot be the security control. Both snippets are simplified for teaching (no password hashing, rate limiting or CSRF protection shown).
Test-Driven Development · 1 min 15 secSlide 09 / 13 · 12:00–13:15

Red, green, refactor

1. Red: write a failing test→2. Green: make it pass→3. Refactor: tidy it up↺

Step 1 · Red

One small test for the next required behaviour. Run it. Watch it fail.

REQ-05: a password shorter than eight characters is rejected.

Step 2 · Green

Write the least code that satisfies the test. Nothing clever yet.

Check the length. That is all, for now.

Step 3 · Refactor

Improve the code while the test keeps passing. The test is the safety net.

Rename, extract, simplify. Behaviour unchanged.

What should happen when we run the test before writing the implementation?
Then round again for the next small behaviour. TDD is not “write every test first, then build the whole application”. It is a short, repeated cycle.
Test-Driven Development · 1 min 15 secSlide 10 / 13 · 13:15–14:30

The cycle, in code

Red: the tests come first

# REQ-05
def test_short_password_rejected():
    assert is_valid_password("abc123") is False

def test_eight_characters_accepted():
    assert is_valid_password("abcd1234") is True

Green: the minimum that passes

# passes both tests
def is_valid_password(password):
    return len(password) >= 8

Try it: run the two tests against three versions

A JavaScript copy of these tests runs in your browser. Nothing is uploaded. Predict each result before you press the button.

Not run yet. Predict first, then run.
What the runs show: with no function, the tests fail for the wrong reason (the function does not exist). return False passes the first test but not the second. The second test is what forces a real length check: each new test drives the code one step on.
Deliberately simplified: eight is illustrative. NIST SP 800-63B-4 requires at least 15 characters when a password is the only factor (eight with multi-factor authentication). A passing test is evidence about the cases covered, not proof of correctness.

Code-then-test and TDD

Two approaches side by side. The first row is identical on purpose.
Code-then-testTest-driven development
Requirements identifiedRequirements identified
Implement the featureWrite one small failing test
Write the tests afterwardsWrite the minimum code that passes
Fix whatever the tests revealRefactor, with the tests still passing
Can suit prototypes and exploratory workGives feedback during implementation

“Which approach gives feedback earlier about whether one small requirement is satisfied?”

“The important distinction is not the type of test. It is when the test enters the process, and how strongly it shapes the design.” Neither approach is universally better.

After the session · practise and explore

Independent study

Core task (30 minutes)

In Python, write the two tests for REQ-05 with pytest and watch them fail. Implement is_valid_password until both pass. Then add a third test for a boundary case of your choice, and push your work to GitHub so the tests run in CI.

Extension: security (20 minutes)

Write a test for REQ-06: a request to /dashboard with no valid session must be rejected with 401, even if the browser claims the user is logged in. Use only your own practice project.

Human review: did the AI miss anything?

An AI assistant wrote only one test and says: “The password rule is done.”

def test_short_password_rejected():
    assert is_valid_password("abc123") is False
